# NSE/BSE Intraday Opportunity Scanner Implementation Plan

## Objective

Build a notification-first C#/.NET automation system for Indian equity intraday opportunities. The workflow is:

1. End-of-day candidate generation
2. Pre-market filtering
3. Opening-range validation
4. Live validation
5. Continuous monitoring
6. Notification trigger

The system must clearly separate signal generation from order execution. MVP scope must not place orders, store broker credentials, or include live trading automation. Risk rules start with configurable capital and planned-risk limits, defaulting to `₹20,000` deployable capital and `₹200-₹400` maximum planned risk per trade.

## Current Repository State

The repository currently contains only `README.md`, so this is effectively a greenfield implementation. The plan below proposes the initial .NET solution structure and boundaries.

### `UniversalEngine.Domain`

Pure business rules with no network, database, scheduler, or framework dependencies.

Core models:

- `Instrument`: symbol, exchange, ISIN, tick size, lot size if relevant
- `DailyBar`: OHLCV and delivery metrics
- `IntradayBar`: timestamped OHLCV
- `Candidate`: instrument plus EOD score and reasons
- `Signal`: normalized opportunity generated by strategy logic
- `TradePlan`: entry, stop, target zones, quantity, planned risk
- `RiskProfile`: capital, max risk amount, max open signals, per-symbol limits
- `MarketSession`: NSE/BSE session calendar and phase
- `NotificationEvent`: user-facing message payload

Important value objects:

- `Money`
- `Price`
- `Quantity`
- `BasisPoints`
- `RiskAmount`
- `Exchange`
- `SignalDirection`
- `SignalConfidence`

### `UniversalEngine.Infrastructure`

Adapters for external systems and persistence.

Initial adapters:

- `IMarketDataProvider`
- `IHistoricalDataProvider`
- `IIntradayFeedProvider`
- `IExchangeCalendarProvider`
- `INotificationSender`
- `IScannerRepository`
- `IClock`

Provider implementations can start as file-backed or mock data for safe local testing, then add real market-data vendors behind the same interfaces. Dhan should be the default primary provider, with Zerodha and Groww as configurable alternatives.

Suggested persistence:

- SQLite for MVP local persistence
- EF Core or Dapper, chosen consistently at implementation time
- Tables for instruments, daily bars, candidates, scanner runs, signals, trade plans, monitor state, and notifications

Do not store broker credentials. If broker integration is ever introduced later, keep credentials outside the repository and outside scanner-domain storage.

### `UniversalEngine.Worker`

Long-running background process.

Responsibilities:

- Schedule EOD generation after market close
- Schedule pre-market filtering before market open
- Run opening-range validation after the configured opening window
- Run live validation and monitoring during market hours
- Retry transient failures
- Emit metrics and structured logs

Recommended implementation:

- .NET Worker Service
- Hosted services for scheduled jobs
- Quartz.NET or Hangfire if durable scheduling is needed
- Plain `BackgroundService` with persisted checkpoints for MVP

### `UniversalEngine.Api`

Optional thin HTTP surface for local dashboards or integration later.

MVP API endpoints:

- `GET /health`
- `GET /scanner/runs/latest`
- `GET /candidates/latest`
- `GET /signals/active`
- `GET /notifications/latest`

The first implementation can skip the API if the worker and tests are enough, but keeping the project boundary in the plan avoids mixing UI/API concerns into the worker.

## Market Data Abstractions

Use interfaces from the application layer and concrete implementations in infrastructure.

```csharp
public interface IMarketDataProvider
{
    Task<IReadOnlyList<DailyBar>> GetDailyBarsAsync(
        IReadOnlyList<Instrument> instruments,
        DateOnly from,
        DateOnly to,
        CancellationToken cancellationToken);

    Task<IReadOnlyList<IntradayBar>> GetIntradayBarsAsync(
        Instrument instrument,
        DateOnly date,
        TimeOnly from,
        TimeOnly to,
        BarInterval interval,
        CancellationToken cancellationToken);
}
```

Design notes:

- Normalize all timestamps to exchange-local time plus UTC storage where needed.
- Keep exchange-specific holidays and special sessions in `IExchangeCalendarProvider`.
- Treat data freshness as part of validation, not as an assumption.
- Persist raw-ish bars and normalized bars separately only if source reconciliation becomes necessary.

## Signal Engine

Split signal generation into stages that mirror the workflow.

### EOD Candidate Generation

Inputs:

- Daily OHLCV
- Previous day range
- Volume expansion
- Delivery percentage if available
- Gap context
- Relative strength versus index/sector
- Liquidity filter

Outputs:

- Ranked candidates
- Reason codes
- Rejection reasons for observability

Example rules for MVP:

- Average traded value above configurable threshold
- Price above minimum liquidity threshold
- Volume expansion versus 20-day average
- Closing near day high for long candidates or near day low for short candidates
- Avoid instruments with missing or stale daily data

### Pre-Market Filter

Inputs:

- EOD candidates
- Pre-open indication if available
- News/event flags if available later
- Index/sector bias
- Gap percentage

Outputs:

- Reduced watchlist
- Bias per symbol
- Invalidated candidates with reasons

MVP can run this with prior close and index futures/proxy data if pre-open data is unavailable.

### Opening-Range Validation

Inputs:

- First 5/15/30 minute bars
- Opening range high/low
- Relative volume
- Gap hold/fade behavior

Outputs:

- Validated setup candidates
- Proposed entry trigger, stop, and invalidation level

### Live Validation

Inputs:

- Latest intraday candles or ticks
- Breakout/breakdown confirmation
- Volume confirmation
- Spread/liquidity constraints
- Market trend filter

Outputs:

- `Signal`
- `TradePlan`
- notification eligibility

### Continuous Monitoring

Inputs:

- Active signals and trade plans
- Latest intraday prices
- Time-based invalidation rules
- Stop/target proximity

Outputs:

- Signal still valid
- Signal invalidated
- Target hit notification
- Stop breached notification
- End-of-day expiry notification

## Risk Engine

Hard-coded MVP defaults should be configurable:

- Capital: configurable, default `₹20,000`
- Minimum risk per trade: configurable, default `₹200`
- Maximum risk per trade: configurable, default `₹400`
- Maximum planned risk percent: `1%-2%`
- Maximum active signals: start with `1-3`
- No averaging down
- No order placement

Position sizing:

```text
riskPerShare = abs(entryPrice - stopPrice)
quantity = floor(maxRiskAmount / riskPerShare)
notional = quantity * entryPrice
quantity must also satisfy notional <= availableCapital
plannedRisk = quantity * riskPerShare
```

Validation rules:

- Reject if stop distance is zero or too tight for tick size.
- Reject if planned risk exceeds configured maximum risk.
- Reject if planned risk is below configured minimum risk unless configured to allow small-size alerts.
- Reject if required notional exceeds configured capital.
- Reject if quantity is zero.
- Include risk amount and quantity in every notification.

## Notifications

Notification-only is the first production boundary.

Recommended interface:

```csharp
public interface INotificationSender
{
    Task SendAsync(NotificationEvent notification, CancellationToken cancellationToken);
}
```

Initial channels:

- Console/log notification for local development
- Email or Telegram later
- Webhook later

Notification payload should include:

- Symbol and exchange
- Direction
- Entry trigger
- Stop
- Target or trail logic
- Quantity
- Planned risk in rupees
- Reason codes
- Data freshness timestamp
- Clear disclaimer that no order was placed

## Scheduler

Suggested default session timing for NSE/BSE equities:

- EOD generation: after market close and data availability buffer
- Pre-market filter: before open
- Opening-range validation: after chosen opening range window
- Live validation: every 1-5 minutes during market hours
- Continuous monitoring: every 15-60 seconds during active signal windows, depending on data cost and provider limits

Implement schedule configuration using options classes:

- `MarketScheduleOptions`
- `ScannerOptions`
- `RiskOptions`
- `NotificationOptions`
- `MarketDataOptions`

## Failure Handling

Required behaviors:

- Skip signal generation when market data is stale or incomplete.
- Degrade to notification of system issue rather than generating uncertain signals.
- Use retries with backoff for transient data provider failures.
- Use idempotency keys for notifications to avoid duplicate alerts.
- Store scanner checkpoints so a restart can resume cleanly.
- Rate-limit notifications per symbol and per signal type.
- Mark every rejected candidate with a machine-readable reason.

Sensitive values:

## MVP Roadmap

### Phase 1: Domain and Local Backtest Harness

- Create solution and projects.
- Implement domain models and risk sizing.
- Add tests for risk sizing and rejection cases.
- Add file-backed historical data provider using CSV fixtures.
- Generate EOD candidates from local sample data.

### Phase 2: Workflow Orchestration

- Implement application services for EOD, pre-market, opening-range, live validation, and monitoring.
- Add scanner run persistence.
- Add rejection reasons and reason-code tests.
- Add console notifications.

### Phase 3: Worker Automation

- Add worker project.
- Schedule each workflow stage.
- Persist checkpoints.
- Add structured logs and health checks.
- Add idempotent notification delivery.

### Phase 4: Real Market Data Provider

- Add provider adapter behind existing interfaces.
- Add data freshness checks.
- Add provider throttling and retries.
- Keep file-backed provider for tests and local replay.

### Phase 5: Production Hardening

- Add real notification channel.
- Add monitoring dashboard/API if needed.
- Add alerting for system failures.
- Add end-to-end replay tests for known market days.
- Add deployment documentation.

### Phase 6: Optional Execution Boundary

Only after the notification system is stable, a separate execution project can be considered. It should consume approved `TradePlan` objects and remain isolated behind explicit manual enablement. This phase is intentionally out of MVP scope.

## First Implementation Pull

Recommended first code change:

1. Create `UniversalEngine.slnx`.
2. Add `Domain`, `Application`, `Infrastructure`, `Worker`, and test projects.
3. Implement `RiskOptions`, `TradePlan`, `RiskSizingService`, and core tests.
4. Add CSV fixture support for daily bars.
5. Implement `EodCandidateGenerationService` with transparent reason codes.

This gives the repository a useful spine without touching live data, broker APIs, or order execution.
